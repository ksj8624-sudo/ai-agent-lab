# Web Platform Rules

## 프로젝트

React Web 프로젝트에서 작업할 때 항상 아래 규칙을 따른다.

현재 프로젝트 구조와 코딩 스타일을 우선하며,
요청 범위를 벗어난 리팩토링은 하지 않는다.

---

## 기술 스택

- Language: TypeScript
- UI: React
- Build Tool: Vite
- Routing: 기존 React Router 구조
- Network: 기존 API Client 또는 `fetch`
- Async: `async/await`
- State: 기존 React State, Context, Hook 또는 프로젝트의 기존 상태 관리 방식
- Styling: 프로젝트에서 현재 사용하는 CSS 및 스타일링 방식

- 새로운 라이브러리는 임의로 추가하지 않는다.

- 실제 프로젝트가 위 구조와 다르면
- 문서보다 현재 실행 코드를 우선한다.

---

## 아키텍처

현재 프로젝트에서 사용하는 계층과 파일 구조를 유지한다.

예:

```text
Page
↓
Component
↓
Hook 또는 상태 관리
↓
API Client
↓
Backend
```

프로젝트에 별도의 Hook, Service, Repository 계층이 없다면
다른 플랫폼 구조를 맞추기 위해 임의로 추가하지 않는다.

새 기능도 현재 프로젝트의 구조를 우선한다.

---

## React 규칙

- 함수형 컴포넌트를 사용한다.
- 기존 Page와 공통 Component를 우선 재사용한다.
- 화면 컴포넌트에 비즈니스 로직을 과도하게 작성하지 않는다.
- 반복되거나 독립적인 UI만 의미 있는 단위로 분리한다.
- 단순히 코드 줄 수를 줄이기 위한 과도한 Component 분리는 하지 않는다.
- 기존 Routing과 화면 이동 구조를 유지한다.
- 기존 색상, 폰트, 간격, 버튼, 입력 필드 스타일을 우선 재사용한다.
- 모바일과 데스크톱에서 레이아웃이 깨지지 않도록 반응형을 고려한다.
- 불필요한 고정 너비와 하드코딩을 최소화한다.
- 접근 가능한 HTML 요소와 적절한 label, button, form 구조를 사용한다.

---

## 상태 관리

- 현재 프로젝트에서 사용하는 상태 관리 방식을 유지한다.
- 단순한 화면 상태는 지역 State를 우선 사용한다.
- 여러 화면에서 공유되는 상태만 기존 Context 또는 전역 상태를 사용한다.
- 새로운 전역 상태 관리 라이브러리를 추가하지 않는다.
- Loading, Success, Empty, Error 상태를 명확히 구분한다.
- 요청 시작 전 이전 오류 상태를 적절히 초기화한다.
- 요청 성공 및 실패 후 Loading 상태가 반드시 해제되도록 한다.
- 중복 요청이 발생하지 않도록 필요한 경우 버튼을 비활성화한다.
- State를 직접 변경하지 않는다.

---

## Hook 규칙

- Hook은 컴포넌트 최상위에서 호출한다.
- 조건문, 반복문, 중첩 함수 안에서 Hook을 호출하지 않는다.
- useEffect의 의존성 배열을 임의로 생략하지 않는다.
- 불필요한 useEffect를 추가하지 않는다.
- 계산 가능한 값은 State로 중복 저장하지 않는다.
- useMemo와 useCallback은 실제 필요가 있을 때만 사용한다.
- Custom Hook은 여러 컴포넌트에서 재사용하거나 복잡한 상태 로직을 분리할 때만 만든다.

---

## API

- 기존 API Client와 Base URL 관리 방식을 우선 재사용한다.
- URL을 새로 하드코딩하지 않는다.
- 기존 API 계약을 임의로 변경하지 않는다.
- Request 및 Response 필드명을 임의로 변경하지 않는다.
- Backend API 명세가 존재하면 해당 명세를 우선한다.
- HTTP Status를 확인하고 실패 응답을 정상 응답처럼 처리하지 않는다.
- API 오류, 네트워크 오류, JSON 파싱 오류를 가능한 범위에서 구분한다.
- Nullable 응답은 TypeScript 타입에서 명확히 표현한다.
- 장시간 Agent 요청에는 기존 Timeout 정책을 유지한다.

- Review와 Plan처럼 API 계약이 서로 다르면
- 억지로 하나의 Request 또는 Response 타입으로 합치지 않는다.

---

## TypeScript 규칙

- 가능한 한 구체적인 타입을 사용한다.
- 불필요한 any를 추가하지 않는다.
- API Request 및 Response 타입을 명확히 정의한다.
- 서버 응답에 없는 필드를 필수 타입으로 추가하지 않는다.
- Type Assertion으로 오류를 숨기지 않는다.
- 기존 네이밍과 타입 파일 배치 방식을 유지한다.
- 사용하지 않는 타입, 변수, Import를 남기지 않는다.
- null과 undefined의 사용은 기존 프로젝트 규칙을 따른다.

---

## Form 및 입력 처리

- 기존 입력 State와 parameter name을 유지한다.
- 입력값을 API 계약과 다르게 변환하지 않는다.
- 빈 입력 요청을 방지한다.
- 필요한 경우 앞뒤 공백을 제거한다.
- 검증 오류와 서버 오류를 구분해서 표시한다.
- 버튼 중복 클릭을 방지한다.
- 기존 Form 구조가 있다면 재사용한다.
- 로그인 등 현재 API 연동이 없는 화면에는 임의로 인증 API를 추가하지 않는다.

---

## 오류 처리

- 사용자에게 표시할 오류와 개발 로그를 구분한다.
- 민감한 요청값, Token, 비밀번호를 Console에 출력하지 않는다.
- 오류가 발생해도 화면이 Loading 상태에 고정되지 않도록 한다.
- 기존 Error Component 또는 메시지 스타일을 우선 재사용한다.
- 오류를 숨기기 위해 빈 응답이나 임의의 기본값을 사용하지 않는다.

---

## 스타일링

- 현재 프로젝트의 CSS 구조와 스타일링 방식을 유지한다.
- 기존 공통 클래스와 디자인 토큰을 우선 재사용한다.
- 새로운 CSS Framework를 추가하지 않는다.
- 전역 스타일 변경은 다른 화면에 미치는 영향을 확인한다.
- 특정 화면 변경을 위해 불필요하게 전체 Layout을 수정하지 않는다.
- 인라인 스타일은 기존 프로젝트 규칙에 맞는 경우에만 사용한다.
- 데스크톱과 모바일 화면을 모두 고려한다.

---

## 작업 제한

- Android 또는 iOS 구조를 그대로 복제하지 않는다.
- 새로운 Architecture 도입 금지
- 기존 기능 제거 금지
- 요청 범위 밖 리팩토링 금지
- 신규 패키지 추가 금지
- Vite 또는 TypeScript 버전 변경 금지
- Routing 구조 임의 변경 금지
- API 계약 임의 변경 금지
- Base URL 하드코딩 추가 금지
- .env 또는 보안 파일 수정 금지
- 다른 Page의 불필요한 수정 금지
- Git Commit 및 Push 금지

---

## Cross Platform

Web이 항상 기준 플랫폼인 것은 아니다.

필요한 경우 다음 프로젝트와 UX를 비교한다.

- Android
- iOS

화면 목적, 입력 항목, 버튼 동작, Loading, Empty, Error,
결과 표시와 화면 이동 흐름을 가능한 범위에서 일관되게 유지한다.

단, React, 브라우저, 반응형 Layout, 접근성 등
Web 플랫폼에 맞는 구현 방식을 유지한다.

다른 플랫폼을 그대로 복제하기 위해
Web에 부자연스러운 UI나 구조를 강제로 적용하지 않는다.

---

## 빌드 및 테스트

작업 후 가능한 범위에서 다음을 수행한다.

- TypeScript Compile Error 확인
- 사용하지 않는 Import와 변수 확인
- 변경 화면 확인
- 기존 기능 회귀 확인
- Lint 실행
- Production Build 실행

프로젝트의 실제 Script를 먼저 확인한 뒤 적절한 명령을 사용한다.

예:

```bash
npm run lint
npm run build
```

테스트 Script가 존재하면 관련 테스트도 실행한다.

---

## 완료 보고

다음을 요약한다.

- 변경한 파일
- 주요 변경 사항
- 유지한 기존 구조
- 실행한 Lint, Build 또는 Test 명령
- 빌드 및 테스트 결과
- 확인이 필요한 사항
- 다른 프로젝트 변경 여부
